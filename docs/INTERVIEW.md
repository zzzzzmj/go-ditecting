# 面试讲解手册

## 一分钟项目介绍

> Go-Ditecting 是我基于 CloudWeGo Hertz 开发的工业安全监测平台。采集 API 将 PLC、HMI 和工程师站的结构化事件投递到 NATS；Detector 队列组异步消费，使用可组合规则识别 Modbus 非法写入、爆破、扫描和工艺值异常；结果写入 MySQL，并通过告警指纹和时间窗口聚合。平台提供态势大屏、处置状态流转、Prometheus 指标和 Grafana 面板。为了方便演示，我还设计了不依赖中间件的单进程模式，但两种模式共享完全相同的领域逻辑。

## 关键设计取舍

### 为什么使用异步消息

工业日志可能突发增长。同步检测会把规则耗时和数据库抖动传导到采集端，导致探针阻塞。NATS 将写入路径与检测路径解耦，Detector 可使用同一 queue group 横向扩容。

当前 Core NATS 适合演示低延迟链路，但不保证离线期间的消息持久化。生产化应切换 JetStream durable consumer，并增加最大重试、退避和死信主题。

### 如何避免告警风暴

检测结果通过 `SHA-256(rule_id | asset_ip | source_ip)` 得到指纹。同一指纹、未关闭、且最近一次发生不超过聚合窗口时，不创建新告警，只增加 `occurrence_count` 并更新 `last_seen_at`。

MySQL 实现用事务和 `SELECT ... FOR UPDATE` 串行化同一候选告警。更高吞吐场景可增加由指纹与窗口桶组成的唯一键，再使用原子 upsert。

### 幂等性做到了哪里

事件表的 `event_id` 有唯一约束，重复事件通过 `INSERT IGNORE` 不会重复落事件表。当前检测发生在写入后，重复投递仍可能增加告警次数，这是刻意保留、可在面试中讨论的边界。

生产改进：先用 inbox 表声明事件消费权，只有首次插入成功才执行检测；或在同一事务中保存消费位置、事件和告警。

### 为什么检测规则使用接口

`Rule` 只暴露元数据和 `Match(Event)`，不依赖 HTTP、NATS 或数据库。优势是：

- 每条规则可以做确定性单测；
- 添加规则不需要修改检测编排；
- 可逐步替换为 YAML/DSL、WASM 或远程规则服务；
- 状态型规则可以在内部管理滑动窗口。

### 工业安全和普通日志平台有什么不同

- 资产与生产区域是一等领域对象；
- 风险排序同时关注网络行为与物理工艺后果；
- 控制写入、工作时段、功能码和工艺上下限具有业务含义；
- 生产 OT 网络可用性优先，平台默认只接收被动采集或模拟事件，不主动扫描设备。

## 常见追问

**为什么不用 Kafka？**

本项目消息规模不大，NATS 部署轻、延迟低、Go 客户端成熟，适合教学和作品集。需要长时间保留、回放或更复杂消费语义时可用 JetStream；超大规模日志管道再评估 Kafka。

**Detector 扩容是否安全？**

队列组保证同一条 Core NATS 消息只交给一个活跃实例。数据库层仍需处理重连或重复投递，事件 ID 唯一约束是第一层幂等保护。

**为什么没有直接解析 PCAP？**

平台把“采集/协议解析”和“检测/处置”解耦。PCAP 解析可以作为新 Producer，把归一化后的事件投递到同一主题，不污染核心领域模型。

**如何支持规则热更新？**

将 `RuleInfo` 和条件表达式存入数据库，Detector 订阅配置变更主题，编译为不可变规则集合后用 `atomic.Value` 一次替换，避免读路径加全局锁。
